# Acceptance tests: command line

Tests for the commands of FR-300 to FR-308, run in a terminal in a fresh
copy of the base project. In PowerShell, `$LASTEXITCODE` shows the exit
code of the last command.

Decisions for the whole area:

- ADR-0003: `clap` for the command line, `serde_json` for JSON output.
- Gap: the spec has no requirement for `requimd --help` and
  `requimd --version`. Users need the version to report problems, and the
  VS Code extension carries the same version (FR-501).
- Code: `requimd --version` and `requimd --help` exist, generated by the
  command line library. Errors go to standard error with the prefix
  `requimd:`; every configuration or usage error ends with exit code 2.

## Check command (FR-300)

- Log 2026-10-11: `requimd check [paths]` loads the whole project; the
  paths only filter the output; paths of different projects are a usage
  error.
- Log 2026-10-12: `check` adds and removes lock entries but never changes
  a hash; `--locked` for CI; an unreadable lock stops the check with exit
  code 2 (ADR-0007).
- Q5 (to confirm): columns count bytes, as compilers and Vim's quickfix
  list do, so an umlaut before the position shifts the column.
- Gap: the spec does not say what the file path in the output is relative
  to (current directory or project root), nor how lines are ordered.
- Gap: with `--locked`, exit code 1 means either errors or an outdated
  lock file; only the message tells them apart.
- Code: file paths are relative to the current directory if the file is
  below it, else absolute, with `/` on every platform; lines are sorted by
  file path and position. Paths given to `check` must exist. The lock file
  is written even when errors are found. With `--locked`, an outdated lock
  gives a message on standard error that asks to run `requimd check` and
  commit the lock file.
- Automated: `fr_300_shop_example_has_no_diagnostics`,
  `fr_300_specification_has_no_errors` (checks tests);
  `fr_300_text_output_and_exit_code_1_on_errors`,
  `fr_300_exit_code_0_without_errors`,
  `fr_300_exit_code_2_without_configuration`,
  `fr_300_exit_code_2_on_configuration_error`,
  `fr_300_exit_code_2_on_usage_error`,
  `fr_300_paths_filter_output_but_whole_project_is_loaded`,
  `fr_300_project_root_found_from_subdirectory`,
  `fr_300_locked_writes_nothing_and_fails_if_out_of_date`,
  `fr_300_conflicted_lock_stops_check_unchanged` (cli tests);
  `fr_300_conflicted_lock_is_an_error` (core lock.rs);
  `fr_300_line_and_column_are_one_based` (core source.rs).

### TC-300 Output format and exit codes

`ref: FR-999`; then instead `FR-901` with the word "fast" in its text (a

## Machine-readable output (FR-301)

- Gap: the fields of a JSON diagnostic, and whether line and column are
  0- or 1-based and in bytes, are not specified. A consumer such as a CI
  annotation script depends on them.
- Code: each entry has `file`, `line`, `column`, `end_line`, `end_column`
  (1-based, columns in bytes as in the text output), `severity`, `check` and
  `message`; the array is pretty-printed.

## Init command (FR-303)

- Gap: the name and place of the glossary file are not specified, nor the
  exit code and message when files already exist, nor what happens inside
  an existing project (a nested project, TC-032).
- Code: `init` writes into the current directory without looking for a
  project root, so inside a project it creates a nested project without a
  warning. It creates `requimd.toml` (the template of the built-in defaults)
  and `glossary.md`, prints `created …` or `… exists, left unchanged` per
  file and ends with exit code 0.
- Automated: `fr_303_init_creates_files_and_never_overwrites` (cli tests);
  `fr_303_init_template_parses_to_defaults_plus_glossary` (core config.rs).

## Format command (FR-304)

- Gap: the normal form of separators is not specified (two spaces, as in
  the examples of the spec?). The order in which several placeholders get
  their IDs, across files, is not specified. Whether `fmt` raises `[ids]`
  in the lock file, so that an ID it assigned cannot be assigned again
  before the next `check`, is not specified (BR-002).
- Code: pairs are written as `key: value`, separated by two spaces.
  Placeholders are numbered in the order of file paths and positions. `fmt`
  does not touch the lock file, so an ID it assigned is protected from reuse
  only after the next check or save (BR-002). It prints `formatted <file>`
  or, with `--check`, `would format <file>`. It always formats the whole
  project; it takes no paths.
- Automated: `fr_304_fmt_assigns_ids_and_normalises_metadata` (cli tests);
  `fr_304_placeholders_get_consecutive_ids`,
  `fr_304_metadata_separators_normalised`, `fr_304_formatted_text_is_stable`
  (core fmt.rs).

## Coverage command (FR-306)

- Gap: a total over all use cases, the treatment of extension steps and
  of deprecated use cases are not specified.
- Code: one line per use case, `uncovered:` with the labels, and a last line
  `total: N steps, K covered (P %)`, with P rounded down and 100 % if there
  are no steps. Extension steps, deprecated use cases and placeholder use
  cases count like any other.

## Review command (FR-307)

- Log 2026-10-12: `requimd review --all` marks all suspect links as
  reviewed.
- Gap: the result for an unknown ID, and for an item without suspect
  links, is not specified.
- Code: `review` first records new links, as a check does. For an item it
  also marks the links to its steps. An unknown ID ends with `not found` and
  exit code 1, an argument that is no ID with exit code 2; without suspect
  links it prints `no suspect links`. Each marked link is printed as
  `reviewed <key>`.
- Automated: `fr_307_review_item_step_and_all` (cli tests);
  `fr_307_review_records_current_hash_of_selected_links` (core lock.rs).
