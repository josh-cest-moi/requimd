# ADR-0007 Lock file

Status: **accepted** on 2026-10-12 by the product owner. Amended by
ADR-0010 (proposed): HTML comments are not part of the content hash.

## Context

Suspect links (FR-116) need the state of each link target as of its last
review, and ID assignment (FR-212) needs the highest number ever assigned
per prefix, so deleted IDs are not reused (BR-002). Both live in a file
that is committed with the specification and changed on branches, so merge
conflicts must stay small and readable.

## Decision

The lock file is `requimd.lock` in the project root, in TOML:

```toml
# requimd.lock: generated by requimd, commit it.

[ids]
FR = 106
UC = 12

[links]
"FR-101 impl UC-012.s1" = "8f3a1c0e5b7d2946"
"FR-104 impl UC-012.s2" = "1d9e44b0a2c6f871"
"TC-220 ver FR-104" = "c07b5e19d3a48f62"
```

- `[ids]`: the highest number per prefix ever seen. It never decreases.
- `[links]`: one line per link. The key is source ID, link key and target
  as written (`<source> <key> <target>`); the value is the target's content
  hash at the last review, 16 hex digits.
- Entries are sorted, so the file is deterministic and a merge conflict
  touches only the lines of the links changed on both branches.

The hash is a 64-bit FNV-1a hash implemented in requimd, so its values do
not depend on the Rust version or platform. It covers, for an item, the
title, the metadata except `status`, and the body; for a step, the step
text. Runs of whitespace, including line breaks, count as one space, so
re-wrapping a paragraph or a change of line endings does not make a link
suspect.

Writing:

- `requimd check` adds entries for new links with the current hash, raises
  `[ids]`, and removes entries of links that no longer exist. It never
  changes the hash of an existing entry; only a review does (FR-218,
  FR-307).
- `requimd check --locked` writes nothing and fails if the lock file is out
  of date. CI uses it.
- The language server records new links when a document is saved.
- Links from items without a unique ID (placeholders, duplicates) are not
  recorded until the item has one.
- A rename (FR-214) rewrites the entries of the renamed ID.
- A lock file that cannot be read, for example because of merge conflict
  markers, stops `requimd check` with exit code 2 and is never
  overwritten.

## Considered

- **JSON**: machine-friendly, but multi-line objects per entry make merge
  conflicts larger and harder to resolve by hand.
- **Storing the reviewed text** instead of a hash, to show what changed:
  the lock file would grow to the size of all linked text. A diff view based
  on git history is on the "Later" list.
- **Only explicit commands write the lock**: then a new link is never
  suspect until it is reviewed once, which defeats FR-116.

## Consequences

- `requimd.lock` is committed. A pull request that changes a target and
  reviews its links shows both in the diff.
- Running `requimd check` locally may change `requimd.lock`; this is
  expected, like `Cargo.lock`.
